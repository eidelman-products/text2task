Read this even if every test in this package passed.

A `PHASE_3_RATE_LIMIT_RUNTIME_PASS` result from
`03_RUN_PHASE3_RATE_LIMIT_RUNTIME_TESTS.sql`, optionally combined with a
clean pass from `06_concurrency_runner.mjs`, confirms that, against a
clean disposable PostgreSQL database with all ten migrations applied
exactly as committed:

- `202608030003_client_share_owner_foundation.sql`
- `202608030004_client_share_session_foundation.sql`
- `202608030005_client_share_integrity_and_security.sql`
- `202608050001_client_share_owner_reads.sql`
- `202608060001_client_share_lifecycle_operations.sql`
- `202608060002_client_share_access_operations.sql`
- `202608060003_client_share_configuration_save.sql`
- `202608110001_client_share_publication_intent.sql`
- `202608110002_client_share_management_mapping_metadata.sql`
- `202608130001_client_share_rate_limit_increment.sql`

`public.increment_share_rate_limit_bucket` exists with the exact expected
signature; is executable only by `service_role`; correctly initializes,
increments, and isolates rate-limit buckets by scope/action/identity/
share-link/window exactly as `share_rate_limit_buckets`' own existing
constraints define; computes `window_start`/`expires_at` deterministically
from the server clock, never from caller input; rejects every
unsupported/malformed input before any write; starts a fresh bucket for
a new logical window; and (if the concurrency runner was also executed)
never loses an increment under genuine concurrent load.

## What passing these tests does NOT prove or authorize

- The disposable test fixture (`01_CREATE_TEMP_TEST_FIXTURE.sql`) is a
  deliberately minimal stand-in for the real production tables. It does
  not, and is not intended to, match the real production schema in every
  column, constraint, trigger or default the production tables actually
  carry.
- Passing this package does **not** authorize applying any of the ten
  migrations above to the real Text2Task production project.
- It does not replace a review of the actual production schema for these
  same tables, nor any prior blocking decision documented elsewhere for
  this feature.
- It does not decide, and does not authorize inventing, any rate-limit
  THRESHOLD (requests per minute, PIN attempts per window, projection-
  read thresholds, lockout UX). No such policy exists in this package —
  it proves only that the atomic counting primitive itself works
  correctly. A separate, explicit product decision is required before any
  threshold is enforced against the counts this function returns.
- It does not authorize resuming Phase 3 application implementation —
  session exchange, the browser-session cookie, the public `/share/**`
  route, the fragment-secret exchange, the PIN flow, the projection read,
  security headers, or analytics isolation. Those remain a separate,
  later, explicitly authorized scope this package does not touch at all.
- A successfully *generated* package (file `02` mechanically assembled)
  is not by itself runtime proof of anything — only an actual run of file
  `03` (and, for the concurrency claim specifically, the runner), captured
  in `04_CAPTURE_RESULTS.md`, is.

## Hard rules

- The Production Text2Task project must never receive file `01`, file
  `03`, or the concurrency runner from this package.
- Only the ten original, committed migration files under
  `supabase/migrations/` are ever candidates for Production application —
  and only exactly as written, never as edited copies, and never as the
  generated bundle in file `02` (which exists solely for temporary-project
  SQL Editor convenience).
- Production application of these migrations requires a separate,
  explicit, later decision by the project owner. This package makes no
  such decision and grants no such authorization.
- No production bundle and no production-application script was
  generated by this package or by the agent that produced it.
- No rate-limit threshold/policy was decided or hard-coded anywhere in
  this package.
