## 1. Executive verdict

The backend for Manual Events — the `calendar_events` table, its RLS policies, its ownership/relationship-integrity trigger, the `TimeOnly` contract, the Zod schemas, the repository functions (`createCalendarEvent`/`updateCalendarEvent`/`softDeleteCalendarEvent`), and all three write API routes (`POST /api/calendar/events`, `PATCH`/`DELETE /api/calendar/events/[id]`) — **already exist, are live in production, and require zero changes for this milestone.** Both `POST` and `PATCH` already return a complete, normalized `ManualCalendarEventItem` (the exact same shape the read model returns) suitable for direct, immediate insertion into `WorkCalendarClient`'s existing state — no existing-API-contract gap blocks the UI. This milestone is **primarily UI, plus one new narrow read endpoint** (`GET /api/calendar/options`, §10) — not strictly "UI-only," since the form genuinely needs a safe project/client option source that does not exist today. No existing write API, repository, migration, or database contract needs to change.

**The one genuinely load-bearing architectural decision** is the shared dialog primitive (§7): this repository has **nine** independently hand-rolled overlay implementations already (`DatePickerPopover`, `ProjectUpdateModalV2`'s shell, `ProjectUpdateHistoryModal`, `ResourceManagerModal`, `ResourceNoteEditorModal`, `DuplicateProjectModal`, `TaskDeleteModals`, `UpgradeModal`, and the profile page's inline feedback modal — see §6 for the full inventory), each reimplementing some subset of the same recipe (portal + Escape + outside-click + focus-trap + scroll-lock) with real, confirmed inconsistencies between them. Building the Manual Event dialog as a tenth independent copy would be the exact anti-pattern the task's non-negotiable rules forbid. This mapping recommends extracting one small, genuinely shared primitive — see §7 for its exact scope, modeled on `DatePickerPopover`, the only existing implementation with a real focus trap and a real centered-modal/bottom-sheet split.

**A second, concrete risk was found and is more involved than a simple z-index fix** (§18): nesting the existing `DateField`/`DatePickerPopover` inside the new Manual Event dialog is not just a paint-order problem — `DatePickerPopover` currently portals directly to `document.body` and owns its own independent Escape/outside-click/focus-trap system, entirely separate from `ResponsiveDialog`'s. Simply raising `DatePickerPopover`'s z-index would leave two independent dismissal/focus systems fighting over the same keyboard/pointer events, causing the outer dialog's focus trap to pull focus away from the date picker, duplicate Escape handling, conflicting outside-click behavior, and focus return targeting the wrong layer. This requires a real nested-overlay contract between the two components (§18), not a z-index token alone — though the z-index token remains a useful, additive, supplementary safeguard.

**Native `<select>` is recommended over a custom combobox** (§11) for the Project/Client pickers — this repository has zero precedent for a custom accessible combobox anywhere, and every existing dropdown in the dashboard is a plain `<select>`.

**Local reconciliation using the API's own normalized response** (Option A, §15) is recommended over a full month refetch after every mutation, but — corrected from an earlier pass of this mapping — the existing `requestIdRef`/`requestKey` guard on `WorkCalendarClient`'s GET lifecycle is **not, by itself, sufficient** to prevent a GET that started before a mutation from overwriting that mutation's effect if it resolves afterward for the *same* range/key. A new monotonic `calendarDataVersionRef` guard is required in addition (§15) — this is a real, load-bearing correction, not an optional enhancement.

**Project/client options are capped at 200** (§10), with **explicit, never-silent truncation flags**, and the endpoint always includes the currently-linked project/client in edit mode even when archived or outside the cap — resolving a real display gap the original recommendation (an `{id,title}`-only shape, capped at 50 with no truncation signal) would have left unaddressed.

Realistic estimate: see §29 (revised upward from an earlier pass of this mapping to reflect the added, genuinely non-trivial work in §15 and §18).

### Where "Add Event" belongs (Step 2 answer — Locked decision 2)

**Locked, not an open question.** Add Event is a standalone action rendered by `WorkCalendarClient`, positioned directly above `CalendarToolbar`, aligned to the end/right of that header row. ## 5. Existing Manual Event API contracts (Step 3)

All three files read directly this session (not from the older foundation report alone).

### `POST /api/calendar/events` (`app/api/calendar/events/route.ts`)

- Auth: `supabase.auth.getUser()` → 401 `{error}` if absent.
- Body: `CreateCalendarEventInputSchema.safeParse(body)` → 400 `{error: "Invalid request body"}` on failure (title 1–240 chars trimmed; `eventDate` via `DateOnly` transform; `eventTime` nullable `TimeOnly` transform; `notes` nullable, blank→null, max 5000; `projectId`/`clientId` nullable UUID; `.strict()` — unknown keys, including any client-sent `userId`, are rejected outright).
- Delegates to `createCalendarEvent({supabase, userId, input})`, which calls `validateCalendarEventLinks` first (project/client ownership + soft-delete rejection + the locked "project's client always wins" normalization), then inserts, `.select(CALENDAR_EVENT_SELECT).single()`, then `normalizeCalendarEventRow(data)`.
- **Success**: `201 {success: true, item: ManualCalendarEventItem}` — a **complete, normalized item**, including the resolved `projectTitle`/`clientName` from the embedded join (`normalizeEmbeddedRelation`), ready for direct client-state insertion.
- **Failure shapes**: `400 {error}` (bad body); `401 {error: "Unauthorized"}`; `404 {error: "Linked project not found."}` / `"Linked client not found."` (via `validateCalendarEventLinks`); `400 {error: "Linked project has been deleted."}`; `500 {error}` (insert failure, or the saved row failed to normalize — this last case should be unreachable given the DB's own constraints, but is handled, not assumed).

### `PATCH /api/calendar/events/[id]` (`app/api/calendar/events/[id]/route.ts`)

- `id` path param validated as a UUID **before** touching the database (`z.string().uuid()`) → 400 `{error: "Invalid event id."}`. **This is exactly why the client must never send the item's own `event:${uuid}` id verbatim** — the route expects a bare UUID; see the `parseManualCalendarEventId` helper in §13/§28 (Correction 5).
- Body: `UpdateCalendarEventInputSchema.safeParse(body)` — every field `.optional()`, `.strict()`, `.refine(Object.keys(v).length > 0)` (rejects an empty patch) → 400 on failure.
- Delegates to `updateCalendarEvent`: loads the existing row (404 if not found/not owned/already-soft-deleted — note: **an already-deleted event's PATCH returns 404**, not a special "cannot edit deleted" message — this is a reasonable, consistent choice, not a gap), then **only** re-validates/re-derives `project_id`/`client_id` when the patch actually contains `"projectId"`/`"clientId"` keys (checked via `"key" in input`, never `?? fallback`) — an update touching only `title`/`eventDate`/`eventTime`/`notes` never re-queries `projects`/`clients` at all and cannot possibly rewrite the event's historical client link, mirroring the database trigger's own identical guard exactly (both layers fixed together in the foundation milestone's corrective pass).
- **Success**: `200 {success: true, item: ManualCalendarEventItem}` — again a **complete, normalized item**.
- **Explicit clearing confirmed to work end-to-end**: `UpdateCalendarEventInput`'s all-optional shape means `{eventTime: null}` (key present, value null) is distinguishable from omitting `eventTime` entirely — the repository's `"key" in input` check (not `input.eventTime ?? existing`) is what makes this safe; the same applies to `notes`, `projectId`, `clientId`. Confirmed by direct code reading of `updateCalendarEvent`'s `updates` object construction (`if ("title" in input) updates.title = input.title;` — one line per field, no fallback operators anywhere). See §9/§13 for the exact, corrected rule governing when the form is and is not allowed to include `projectId`/`clientId` in this body (Correction 2).
- **Failure shapes**: `400`/`401`/`404` as above, plus `500 {error: "Could not update the calendar event."}` / `"The updated event could not be read back correctly."`.

### `DELETE /api/calendar/events/[id]` (same file)

- Same `id` UUID validation — same `parseManualCalendarEventId` requirement.
- Delegates to `softDeleteCalendarEvent`: loads the row (404 if not found/not owned); if already soft-deleted, returns success with `alreadyDeleted: true` **without a second write** (true idempotency, not just a non-error status); otherwise sets `deleted_at = new Date().toISOString()` (a `timestamptz` audit stamp, not a `DateOnly`/`TimeOnly` value — does not violate the date-safety rule) and returns `alreadyDeleted: false`.
- **Success**: `200 {success: true, alreadyDeleted: boolean}`. **Note**: this response does **not** echo the deleted item's id (the id is already known client-side — the client only ever calls DELETE using an id it already holds from the item being deleted) — this is sufficient information for the client to remove the item safely (filter its local array by the id it already has), not a gap.
- **Failure shapes**: `400`/`401`/`404`/`500 {error: "Could not delete the calendar event."}`.

### Direct answers to the Step 3 questions

- **Does POST return a complete normalized `ManualCalendarEventItem` suitable for immediate insertion into client state?** **Yes**, confirmed by direct code reading of `createCalendarEvent` → `normalizeCalendarEventRow`, which produces the exact same shape `GET /api/calendar` returns for existing manual events, including the `event:` id prefix.
- **Does PATCH return the same complete normalized item?** **Yes**, identically, via the same `normalizeCalendarEventRow` function (one shared normalizer, not two separately-maintained ones — confirmed reused by both the read-model loader and both write paths).
- **Does DELETE return enough information to remove the item safely?** **Yes** — the caller already has the full item (and its `event:`-prefixed id) before calling DELETE; `{success, alreadyDeleted}` is sufficient to confirm the operation and decide whether to show any special "already removed elsewhere" messaging (optional UX nicety, not required).
- **Are any API-contract gaps present that block the UI?** **None found in the existing write/read routes.** A genuine gap exists in a different place: no existing endpoint safely returns a project/client *option list* for the picker (§10) — this requires one new route, not a change to any existing one.
- **Can the milestone proceed with zero API changes?** **Corrected — no.** Zero changes are needed to any *existing* route, schema, repository function, or migration — that part of the original claim holds. But this milestone does require **one new read-only API route**, `GET /api/calendar/options` (§10), because no safe, narrow, existing source for project/client picker options exists (confirmed by a dedicated research pass, §10). Every earlier or later reference in this report to "UI-only" or "zero API changes" should be read with this correction in mind.

### Security posture confirmed present today (relevant to §20)

- `validateCalendarEventLinks` re-validates project/client ownership — **and archived-project handling is a deliberate, confirmed omission**: it checks `deleted_at IS NULL` on `projects` but does **not** check `is_archived` — meaning the backend will happily accept and link an **archived** (but not soft-deleted) project to a Manual Event today. This is a real, confirmed fact (not an assumption) that directly shapes §9's Project-field recommendation: archived projects are excluded from *new* choices in the picker (a UI courtesy), but an already-linked archived project must still work, since the server does not reject it.
- The database-level `enforce_calendar_event_relationship_integrity` trigger independently re-derives/re-validates the identical rule as a backstop, confirmed still present and still correctly guarded (only runs when the relationship is actually changing) per the foundation milestone's corrective pass.
- Ownership: every `projects`/`clients` lookup is explicitly `.eq("user_id", userId)`-scoped in application code, never relying on RLS alone (matches the universal repo convention). RLS itself (confirmed live in production, foundation report §23) is the backstop, not the only check. The new options endpoint (§10) must follow this identical convention, including for its optional `includeProjectId`/`includeClientId` parameters (§20).

## 7. Recommended shared dialog primitive (Step 4 continued)

**Verdict: extract one small shared primitive** (recommended name: `ResponsiveDialog`, matching the brief's own suggested naming and this repo's `Dashboard*`/`Calendar*` naming conventions — e.g. `app/components/dashboard/ui/responsive-dialog.tsx`). This is justified, not over-engineering: nine independent implementations already exist with real, user-visible inconsistencies (three of them ship with literally zero dismissal handling), and building a **tenth** independent recipe for Manual Events would be the exact anti-pattern the milestone's non-negotiable rules forbid. This is *not* "converting every existing modal" (explicitly out of scope, per the brief) — it is building the Manual Event dialog **on** a new, small, well-tested primitive, leaving the other eight untouched for now (a natural, separate, future cleanup opportunity, not part of this milestone).

### Exact responsibilities the primitive owns

1. **Portal + mount-gate**: `createPortal(children, document.body)`, gated by the existing `useHasMounted()` (`app/components/dashboard/use-has-mounted.ts`) — already the most-used, explicitly-documented-as-canonical technique; do not introduce a fifth gating technique.
2. **Escape-to-close**: one `window` `keydown` listener, calling `onRequestClose()` — never a commit — gated by a caller-supplied `busy: boolean` prop (mirroring the `!isBusy`/`!isSaving` gating already present in 5 of 9 existing implementations) so an in-flight save/delete cannot be Escaped away mid-request. **Corrected (§18)**: this listener must also be suspended entirely whenever a nested overlay (the date picker) is registered active — see responsibility 9, below.
3. **Outside-click dismissal**: `onMouseDown` + `event.target === event.currentTarget` on the overlay (the majority, more-correct technique already used by `DatePickerPopover`/`ProjectUpdateModalV2`/`ResourceManagerModal`/`ResourceNoteEditorModal`/the profile feedback modal — **not** the bare `onClick` a minority of implementations use inconsistently), also gated by `busy` **and by whether a nested overlay is active** (§18).
4. **Body-scroll lock**: lock both `document.body.style.overflow` and `document.documentElement.style.overflow` (the more thorough of the two policies observed), restoring the previous values on cleanup — as an **opt-out** prop (`lockScroll?: boolean`, default `true`), since a future popover-style consumer (mirroring `DatePickerPopover`'s desktop mode) may legitimately not want it.
5. **Desktop/mobile presentation branch**: a new shared `useIsMobile()` hook (extracted from `DatePickerPopover`'s current file-local one, moved to e.g. `app/components/dashboard/ui/use-is-mobile.ts`) backed by `window.matchMedia` against `dashboardBreakpoints.mobile` (900 — the one already-centralized token, standardizing away from the 760/860 magic numbers found elsewhere). The primitive switches between a centered-panel container (desktop) and a bottom-sheet container (mobile), modeled directly on `DatePickerPopover`'s `desktopOverlayStyle`/`desktopPanelStyle` vs. `sheetOverlayStyle`/`sheetPanelStyle` split — the only existing, proven reference for this exact transformation.
6. **ARIA shell**: always renders `role="dialog"`; `aria-modal` is a prop defaulting to `true` (so a future non-modal popover consumer can still opt out, preserving `DatePickerPopover`'s deliberate distinction if it's ever migrated onto this primitive later); requires the caller to pass `aria-labelledby` (preferred — pointing at the caller's own visible heading id, correcting the `aria-label`-despite-a-visible-heading gap found in several existing implementations) or `aria-label` as an explicit fallback.
7. **Focus containment + return**: the Tab-cycling focus trap and the `wasOpenRef`-transition-based "return focus to the caller-supplied trigger ref on any close path" logic, lifted nearly verbatim from `DatePickerPopover` (the only existing implementation with either) — this closes the single biggest, most consistent accessibility gap found across the whole survey (8 of 9 implementations have neither). **Corrected (§18)**: the trap's `keydown` handler must ignore any event whose `defaultPrevented` is already `true` (so a nested overlay's own Tab-handling, if it chose to `preventDefault()`, is never double-processed by the outer trap), and the trap must not run at all while a nested overlay is registered active.
8. **Supplementary z-index token** — see the dedicated nested-overlay resolution (§18): the primitive accepts an optional `zIndex?: number` prop (default `dashboardZIndex.modal`). **This is explicitly a supplementary safeguard, not the fix** for the nested-DatePicker problem — the real fix is responsibility 9, below; a z-index token alone cannot resolve two independent focus/dismissal systems fighting over the same events.
9. **Nested overlay host + context (new, Correction 4)**: `ResponsiveDialog` renders one additional DOM node — a "nested overlay host" — as a **sibling of the dialog panel itself, inside the same portal root** (both are children of the one `createPortal(..., document.body)` call from responsibility 1, above), **not** a descendant of the panel's own scrollable content region. Concretely:
   ```
   ResponsiveDialog portal root
     ├── backdrop
     ├── dialog panel (the scrollable content region — header/fields/footer)
     └── nested overlay host
   ```
   Placing the host as a **sibling** of the panel — rather than nested inside it — is deliberate and load-bearing: a nested overlay portaled *inside* the panel's own `overflow-y: auto` content region would be clipped by that scroll container (and by the panel's `border-radius`, and by the mobile bottom sheet's own scroll/overflow handling, §17) exactly like any other absolutely-positioned descendant of an `overflow` container, regardless of z-index. As a sibling in the same portal root, the host paints above the panel with nothing to clip it. `ResponsiveDialog` provides a React context (e.g. `NestedOverlayContext`) exposing: the host element/ref a nested overlay should portal into instead of `document.body`; a `registerNestedOverlay()`/`unregisterNestedOverlay()` pair a nested overlay calls on open/close to tell the dialog "a nested layer is active, suspend your own Escape/outside-click/focus-trap until I close." This is the actual fix for the nested-DatePicker problem (§18) — full detail, including exactly how `DatePickerPopover` consumes this context and what happens for callers **outside** a `ResponsiveDialog` (unchanged, direct-to-`document.body` behavior), is specified in §18, not repeated here.

### Explicitly left to the caller (the Manual Event form)

- **Initial focus target** — the primitive does not force focus anywhere on open beyond what its focus-trap needs to track; the form decides (first field in create mode, per §9's "Title required, focus first in create mode").
- **All visual chrome** — header, close button, footer/action-row layout are 100% caller-authored (every existing implementation styles these completely differently; there is no shared chrome to extract).
- **Busy/loading state computation** — the caller computes its own `isSaving`/`isDeleting` and passes a plain `busy: boolean`; the primitive has no opinion on *why* something is busy.
- **Nested/confirmation-dialog composition strategy** — `ResourceManagerModal`'s own precedent shows two valid strategies already coexist in this codebase (inline second overlay in the same portal, vs. a fully separate nested dialog instance); the Manual Event delete-confirmation (§14) uses neither — it uses an even lighter **inline button-state change**, requiring no second overlay at all, which sidesteps this choice entirely for that specific sub-flow. The nested overlay host (responsibility 9, above) is a *different* mechanism, purpose-built for the DateField/DatePickerPopover case specifically, not a general-purpose nested-dialog composition tool.
- **Form validation, persistence, and API-call ownership** — entirely the form's concern (§8, below); the dialog primitive has zero knowledge of Calendar, dates, or the Manual Event domain, exactly mirroring how `DatePickerPopover` today has zero knowledge of dates (`Calendar`/`date-field.tsx` supply that as opaque `children`).

### Dialog lifecycle and unsaved changes

Consolidating the full open→close lifecycle (drawing together facts already established above and in §12–§14, so this is the one place to read the complete sequence):

- **Opening**: `WorkCalendarClient` sets `activeDialog`; `ResponsiveDialog` mounts, portals, locks scroll, and (via the form) puts initial focus on the Title field in create mode or the same field pre-filled in edit mode (§9).
- **Initial focus**: owned by the form, not the primitive (per "Explicitly left to the caller," above) — the primitive's focus-trap only takes over Tab-cycling once *something* inside the panel already has focus.
- **Escape**: closes without committing, *unless* (a) the delete-confirm sub-state is active, in which case it steps back to the unconfirmed "Delete" state first (§14), or (b) a nested overlay (the date picker) is currently open, in which case the nested overlay owns Escape entirely and the outer dialog's own Escape handling is suspended (§18) — two independent overrides of the primitive's default single-stage Escape, for two different reasons.
- **Overlay click**: identical to Escape — closes without committing, gated off while `busy` or while a nested overlay is active (§7 point 2/3, §18).
- **Close button**: an explicit `×`/"Close" button, always available except while `busy`.
- **Save**: disabled while invalid or in flight (§12); a successful save closes the dialog and returns focus to the trigger (§12/§13); a failed save keeps the dialog open with values intact (§12/§13/§22).
- **Delete**: gated behind the inline two-step confirm (§14); a successful delete closes the dialog; a failed delete reverts the confirm state and keeps the dialog open (§14).
- **Focus return**: on Save or Cancel (create or edit mode), to the original trigger — the Add Event button (create) or the specific Edit button (edit) — which remains present in the DOM in both cases, since a successful save updates the card in place rather than removing it. On a **successful Delete**, the originating Edit button's card has just been removed from the list by the same mutation reconciliation that closes the dialog (§15), so the button is guaranteed to no longer be connected to the document by the time focus would return — the dialog does not attempt to focus a detached element. The full, corrected fallback chain (§14/§19): check whether the originating trigger is still connected; if not, fall back to the stable **Add Event** button (always present); if that is unexpectedly unavailable too, fall back to the `SelectedDayAgenda` heading via a programmatic ref with `tabIndex={-1}`.
- **Body-scroll restoration**: automatic, on unmount, via the primitive's own cleanup (§7 point 4) — no caller action needed.
- **Mobile virtual keyboard**: no bespoke handling needed; the sheet's own `overflow-y: auto` + non-fixed height already accommodates it (§17).
- **Browser back button**: this milestone does not push any history entry when the dialog opens (matching every existing dialog in the codebase, none of which are URL/history-integrated, §6) — the browser Back button navigates away from `/dashboard/calendar` entirely if pressed while the dialog is open, exactly as it would with no dialog open; this is existing, unchanged Next.js routing behavior, not a new concern this milestone introduces.
- **Double close**: idempotent by construction — `onRequestClose`/`onClose` simply sets `activeDialog = null`; calling it twice (e.g., an Escape keypress racing a click) is a no-op the second time, since there's nothing left to close.
- **Component unmount during save**: covered explicitly in §22's "Dialog closed during request" row — the in-flight mutation is not aborted; its `then` handler still applies the reconciliation logic (§15) against whatever Calendar state is current when it resolves, even though the dialog itself is already gone.

**Is unsaved-change confirmation needed for MVP? No** (Locked decision 6) — no existing dialog anywhere in this codebase has one (§6), and this form is short enough (6 fields) that silent-close-on-Cancel/outside-click/Escape matches house convention throughout.

## 9. Field contracts (Step 6)

Every field's client-side contract, matching the already-live Zod schema exactly (no new server-side rule needed anywhere below for title/date/time/notes — this section maps the UI-side mirror of an existing contract, plus the presentation choices layered on top; Project/Client are corrected below against the new options contract, §10, and the historical-client rule, Correction 2).

- Required. Trim surrounding whitespace before validation and before sending (matches `TitleSchema`'s own `.trim()` — the client should not rely on the server to trim, so the user sees the trimmed value reflected immediately, e.g. in an inline character counter).
- 1–240 characters after trimming (matches `TitleSchema.min(1).max(240)` exactly — no new limit invented).
- Inline validation: show an error the moment the field is blurred empty, or on submit attempt; never block typing.
- Focus first in create mode (the single most useful default focus target when the dialog opens with no prior context).

### Date
- Required. - No UTC conversion anywhere (inherited automatically by reusing `DateField`/`DateOnly` as-is).
- Clicking Add Event defaults `eventDate` to `WorkCalendarClient`'s current `selectedDate` (§4 — zero new plumbing needed, the value is already in scope where the dialog is opened).
- **Nested date-picker note (corrected, §18)**: `DateField`'s own `DatePickerPopover`, when rendered inside the new dialog, integrates with `ResponsiveDialog`'s nested-overlay host/context — a real focus/dismissal handoff, not merely a z-index adjustment. This does not change the Date field's own `value`/`onChange` contract, only how the dialog and the nested popover coordinate focus and dismissal while it's open.

### Time
- Optional. Native `<input type="time">` — **no precedent exists anywhere in this repo for a time input** (confirmed, unchanged from the original mapping's finding), and the foundation milestone's own `TimeOnly` module doc comment explicitly designed itself around exactly this simplicity ("a bare 24h string is sufficient and avoids ever needing timezone-aware parsing"). No repository evidence argues for a custom time-picker popover; a native control avoids adding yet another hand-rolled popover on top of the count in §6's dialog-primitive inventory.
- Strict `TimeOnly` `HH:MM` — matches `TimeOnlySchema`/`parseTimeOnly` exactly; a native `<input type="time">`'s own value is already `"HH:MM"` (no seconds) in every evergreen browser, so no extra stripping/parsing step is needed beyond `parseTimeOnly(input.value)` for validation before submit.
- Empty input value (`""`) means `null`/all-day — must be sent as an explicit `eventTime: null` on both create (the type already requires `TimeOnly | null`, never `undefined`) and on update-to-clear (an explicit `{eventTime: null}` key, not an omitted key — see the "no `value || fallback`" rule below).
- No seconds (native `<input type="time">` without a `step` attribute never produces seconds — do not add a `step` attribute, since that would introduce a seconds granularity the `TimeOnly` contract and the database's own minute-precision `CHECK` constraint both explicitly forbid).
- No `Date` object conversion anywhere in the form (the native input's string value goes straight through `parseTimeOnly`/`TimeOnly`, never through a `Date`).

### Notes
- Optional. Blank/whitespace-only normalizes to `null` — matches `NotesSchema` exactly (the client-side normalization should mirror this so the character-count/validation the user sees matches what will actually be persisted, but the **server remains the authoritative** normalizer regardless of what the client computes — a defense-in-depth double-normalization, not a duplicated validation *rule* since both sides agree on the same rule already codified once in `calendar-schemas.ts`).
- Max 5000 characters (matches `NotesSchema` exactly).
- `<textarea>`, preserving line breaks on display (the existing `SelectedDayAgenda`/`CalendarAgendaItem` read-only rendering already does this via `white-space: pre-line` — the form's own textarea does this natively, nothing new to build).
- No HTML — a plain `<textarea>` value is never rendered as HTML anywhere in this codebase's Calendar surfaces (confirmed: `CalendarAgendaItem`'s notes rendering is plain text interpolation, never `dangerouslySetInnerHTML`) — the new form does not change this.

### Project
- Optional. **Native `<select>`** (§11), populated from the new options endpoint's `CalendarProjectOption[]` (§10): `{id: string; title: string; clientId: string | null; clientName: string | null; isArchived: boolean}` — **corrected from an earlier pass of this mapping, which recommended an `{id, title}`-only shape**; the form genuinely needs `clientId`/`clientName` (to display and lock the Client field, Correction 2) and `isArchived` (to render an "(archived)" affix and to distinguish an option the user is choosing fresh from one that's already linked).
- **Archived-project rule, precise**: archived (not deleted) projects are **excluded from the normal option list** the endpoint returns for *new* choices (a UI courtesy — the server does not reject an archived project's id if sent anyway, since only `deleted_at` is checked server-side, §5). But an event's **already-linked** project, if archived, is **always** included in the options response (via `includeProjectId`, §10) so it still displays correctly and remains editable — it is never silently dropped.
- **Deleted projects are never selectable** — this is also server-enforced (404 if attempted anyway via a stale/tampered request), so the options endpoint excludes them unconditionally, with no `include`-style override (there's nothing valid to "still show" for a genuinely deleted project on an event whose FK already went `null`, §7 of the original mapping's still-valid `on delete set null` finding).
- Selecting a project derives/displays its client from the **option's own `clientId`/`clientName` fields** — see the Client section below for the exact, corrected four-scenario rule (Correction 2) governing exactly when this happens and when the event's own stored historical client is shown instead.

### Client — the historical-client rule (restated in this corrective pass against two independent dirty flags, replacing an earlier, internally-inconsistent version of this section)

Optional. Native `<select>`, populated from the options endpoint's `CalendarClientOption[]` (§10): `{id: string; name: string}`.

**Locking rule**: Client is **locked** (disabled, showing a derived value) whenever Project currently has a value — whether that's the event's original, untouched project or a newly selected one. Client is **independently editable only** when Project is currently cleared (no project selected).

**Dirty tracking uses two independent boolean flags — never a single combined "relationship touched" boolean** (an earlier pass of this mapping used one combined flag; that framing is corrected here). Both flags are live equality checks against the values captured once, when the dialog opened (`initialProjectId`, `initialClientId`) — never "was this field interacted with at some point" flags, which can go stale or misfire on a no-op interaction:

- **`projectChanged = currentProjectId !== initialProjectId`.** A pure value comparison. If the user clears Project and then reselects the *exact original* project, `currentProjectId` once again equals `initialProjectId` and `projectChanged` is `false` — even though the field was genuinely interacted with along the way; the net value is unchanged, so nothing is sent.
- **`clientChanged = currentClientId !== initialClientId`**, but this flag is tracked and meaningful **only while Client is independently editable** (Project currently cleared). While Project has a value and Client is locked/derived, `clientChanged` does not apply — any value it held from an earlier moment when Client was briefly independently editable (during a clear) is **discarded and ignored** once Project is set again and re-locks Client. There is no "carry forward a stale client edit across a project re-selection" case to support.

The form's display/lock behavior and PATCH-body construction follow **exactly four scenarios** — no other rule, and no scenario may be collapsed into another:

1. **Create mode, a project is selected.** The Client field displays that project **option's current** `clientName` (from the selected `CalendarProjectOption.clientName`) and becomes **locked**. Create mode has no "initial" values to diff against — the two dirty flags are an edit-mode concept only; create mode simply sends whatever Project/Client the form ends with. The server remains authoritative — whatever the form displays is a preview, not a value the client is trusted to persist verbatim; the actual persisted `clientId` is whatever the server derives at write time (§5/§7 of the original mapping's still-valid normalization rule).
2. **Edit mode, `projectChanged` is `false`.** Project's current value equals its initial value (including the "cleared then reselected the same project" case above). Client displays and preserves the **event's own stored** `clientId`/`clientName` exactly as loaded — **never** silently replaced by the linked project's *current* client, even if that project's client has since changed. The outgoing PATCH body **omits `projectId` and `clientId` entirely** (not `null`, not the unchanged value — omitted, so the server never re-derives the relationship at all, §5). This is the exact, already-live, already-tested server/database guarantee (the foundation milestone's dedicated 7-test regression suite, §5) — the form's only job is to never construct a PATCH body that would defeat it by including those keys when the net project value hasn't actually changed.
3. **Edit mode, `projectChanged` is `true` and the new value is non-null** (a different project is now selected, or a project is selected after having been cleared earlier in the same session, landing on a value that differs from the initial one). The Client field switches to displaying the **newly-selected project's current** `clientName` and (re-)locks — this **overrides and discards any `clientChanged` state** accumulated while Client was briefly independently editable during an intervening clear (per the locking-rule note above). The outgoing PATCH includes `projectId` (the new value) **only** — it must **not** include a client-derived `clientId`; the server remains the sole authority that derives and persists the correct client relationship from the project (§5), and it is the PATCH response's own normalized `clientId`/`clientName` — never anything the client computed or displayed — that the mutation-reconciliation step (§15) splices into calendar state.
4. **Edit mode, `projectChanged` is `true` and the new value is `null`** (project cleared). The Client field **unlocks** and becomes independently editable; `clientChanged` now begins to apply. The outgoing PATCH includes `projectId: null`. If `clientChanged` is `false` (Client left alone after unlocking), `clientId` is **omitted** from the PATCH entirely — the client value hasn't changed from the server's point of view, and the server's stored `client_id` for that event is left untouched. If `clientChanged` is `true` (the user changed or cleared Client while it was unlocked), `clientId` is **included**, set to its new value or `null`.

**When the selected project has no client** (`clientId`/`clientName` both `null` on the option): display "No client," still locked (scenarios 1 and 3) — a real, valid, already-supported case.

**Selecting a new project after clearing it** is the concrete case that motivates discarding `clientChanged`: Project cleared (scenario 4, Client unlocks) → user independently picks a different Client while unlocked (`clientChanged` becomes `true`) → user then selects an actual project (scenario 3 applies, since the new value is non-null and differs from initial). At that point Client re-locks to the newly-selected project's current client, `clientChanged`'s `true` value from the intervening step is discarded/ignored, and the PATCH sends `projectId` only — never the independently-selected `clientId` the user picked while Client was briefly unlocked, since the server derives the relationship from the project regardless.

### Explicit clearing (time, notes, and the project/client relationship)
- Must survive UI state → request body → Zod → repository as an **explicit `null`** (for time/notes when cleared, and for `projectId`/`clientId` when their respective value genuinely changed to cleared), never an omitted key when something genuinely changed, and never a `value || fallback`/`value ?? fallback` collapse. This is not a new rule to invent — it is the exact rule the backend already enforces and already has dedicated tests for (§5) — the form's own request-body-assembly function is the **only** new code that needs to get this right, by comparing each field's current value against its initial value (a per-nullable-field dirty check for time/notes, plus the two independent `projectChanged`/`clientChanged` value-comparison flags described above for the relationship) rather than by any falsy-value coercion or interaction-based "was touched" tracking.

## 10. Project/client option-source recommendation (Step 7)

A dedicated, parallel, read-only research pass confirmed: **there is no safe, narrow, existing source to reuse.** Specifically —

- **`DashboardClient` holds no deduplicated project or client list at all.** It only ever fetches full `TaskRow[]` (`GET /api/tasks`/`GET /api/tasks/snapshot`), each row carrying its own embedded, non-deduplicated `project`/`client` object; the SPA's only "grouping" is by client *name* for display, not a project/client entity list. Coupling the new routed Calendar page to this component to "borrow" its data would require pulling in the full 1800+-line component and its entire task-loading machinery — exactly the coupling this milestone must avoid.
- **The one existing narrow-projection precedent, `GET /api/calendar/unscheduled` (`lib/calendar/load-unscheduled-projects.server.ts`), is close but not directly reusable**: it deliberately filters to `deadline_date IS NULL AND status != 'Done'` (correct for *its own* Unscheduled Projects panel, out of scope this milestone) — using it as-is for a general project picker would silently hide any project that already has a deadline or is marked Done, which is wrong for an event-linking picker (a user should be able to link an event to any of their active projects, deadline or not).
- **`CALENDAR_EVENT_SELECT` (`lib/calendar/calendar-events-repository.server.ts`) already embeds `{id, title}` for projects and `{id, name}` for clients when reading back a calendar event** — this confirms the *minimum* projection this feature already relies on, but (corrected from an earlier pass of this mapping) it is **not sufficient on its own** for the options endpoint, which additionally needs each project's current `clientId`/`clientName` (for the Client-field lock/display behavior, §9/Correction 2) and `isArchived` (to distinguish new-choice-eligible projects from an already-linked archived one, §9).
- **Clients have no confirmed `is_archived`/`deleted_at` column exercised anywhere in the codebase** — every existing client query filters only by `user_id`. This is a real, confirmed gap in the current schema/convention (not something to invent a fix for here) — the client option list should simply not attempt to filter by archived/deleted status beyond whatever `.eq("user_id", ...)` already provides, since no such column is known to exist or be populated.
- **Scale is genuinely unconfirmed** — the only real per-user list-size precedent anywhere in the codebase before this milestone was `load-unscheduled-projects.server.ts`'s own `DEFAULT_UNSCHEDULED_PROJECT_LIMIT = 50`. This milestone's own locked product decision (§3) sets the options endpoint's cap at **200**, a deliberately higher, explicitly-chosen number — not simply inherited from that unrelated panel's own, much smaller, precedent.

### Corrected option shapes (Correction 1)

```ts
// lib/calendar/calendar-types.ts — additive only, no existing type's shape changes

export type CalendarProjectOption = {
  id: string;
  title: string;
  clientId: string | null;
  clientName: string | null;
  isArchived: boolean;
};

export type CalendarClientOption = {
  id: string;
  name: string;
};

export type CalendarOptionsResult = {
  projects: CalendarProjectOption[];
  clients: CalendarClientOption[];
  projectsTruncated: boolean;
  clientsTruncated: boolean;
};
```

`CalendarProjectOption` **replaces** an earlier, incorrect recommendation in a prior pass of this mapping that specified `{id, title}` only — that shape could not have supported the Client field's lock/display behavior (§9/Correction 2) or the archived-project affix (§9), and every section of this report that still referenced an `{id, title}`-only project option shape has been corrected to this one.

### Recommended route: `GET /api/calendar/options`

```
GET /api/calendar/options?includeProjectId=<uuid>&includeClientId=<uuid>
```

- Both `includeProjectId` and `includeClientId` are **optional** query parameters. `CalendarEventForm`, when opening in **edit mode**, passes the event's own currently-linked `projectId`/`clientId` (if any) as these parameters — this is how the endpoint guarantees the currently-linked project/client is always present in the response, even if archived (project) or outside the normal 200-item cap (either).
- **Both parameters must be ownership-validated exactly like every other project/client lookup in this codebase** (`.eq("id", includeProjectId).eq("user_id", userId)`, mirroring `validateCalendarEventLinks`'s own pattern, §5/§20) — an id that doesn't resolve to a row owned by the requesting user is **silently omitted** from the response (fail closed), not surfaced as an error and not permitted to leak whether a foreign id exists. This is a read endpoint serving a UI convenience parameter, not a place to trust client-supplied ids without re-validating ownership (§20).
- **Response shape**: `{success: true, ...CalendarOptionsResult}` (matching this codebase's `{success: true, ...}` convention throughout the Calendar feature).
  - `projects`: active (non-deleted, non-archived) owned projects, `{id, title, clientId, clientName, isArchived: false}`, ordered `title` ascending — **plus**, if `includeProjectId` resolved to an owned project not already in that set (because it's archived, or because it fell outside the 200-item normal cap), it is appended (after slicing, see below) with `isArchived` reflecting its real state (`true` for an archived included project).
  - `clients`: all owned clients (no archived/deleted filter — none is known to exist, §10 above), `{id, name}`, ordered `name` ascending — plus, if `includeClientId` resolved to an owned client outside the normal cap, it is appended after slicing.
  - `projectsTruncated` / `clientsTruncated`: `true` whenever the *normal* (non-included) result set for that type actually exceeded the cap — **this flag must always be present and accurate; truncation is never silent** (Locked decision 9). The client only needs to check these two booleans, never infer truncation from array length.
- **How the truncation flag is computed without an expensive exact-count query (locked implementation)**: a plain `.limit(200)` alone cannot tell the difference between "exactly 200 matching rows exist" and "201+ matching rows exist, cut down to 200" — both return exactly 200 rows. The correct, cheap mechanism, which this report locks as the implementation:
  1. Define `const OPTIONS_LIMIT = 200`.
  2. The **normal** project query (no `includeProjectId` involved yet) requests `.limit(OPTIONS_LIMIT + 1)` — i.e. 201 rows — the same single query, no second round-trip.
  3. `projectsTruncated = returnedProjects.length > OPTIONS_LIMIT` (i.e. the query actually returned the 201st row).
  4. The normal `projects` array returned to the client is then **sliced to the first `OPTIONS_LIMIT` (200) rows** — the 201st row (if present) was only ever used to compute the boolean and is discarded, never shipped to the client as a 201st "normal" option.
  5. The identical `OPTIONS_LIMIT + 1` / slice-to-`OPTIONS_LIMIT` / length-comparison pattern is used independently for the `clients` query and `clientsTruncated`.
  6. If `includeProjectId`/`includeClientId` were provided, that ownership-validated lookup is a **separate, single-row query**, run **after** the normal query has already been sliced to 200 — its result (if any) is appended to the already-sliced 200-item array and de-duplicated against it (if the included project/client was already present in the first 200, it is not appended a second time). **This appended value never alters `projectsTruncated`/`clientsTruncated`** — those flags describe only whether the *normal* result set was cut down, not whether an included value happened to be added on top.
  - **The true maximum response size is therefore 201 items per type** in the one edge case where the normal set is already truncated to 200 *and* a separately-included linked value falls outside that 200 and gets appended — exactly the same practical ceiling as before, just reached via a correct, single-extra-row-per-query mechanism rather than an implied (and never-specified) exact-count query.
- **Ordering**: `title ascending` for projects, `name ascending` for clients — a new, but clearly-justified, convention (no existing project/client query orders alphabetically server-side; every existing one orders by `created_at desc`, which is the wrong feel for a picker a user scans by name). This is a small, deliberate, defensible deviation, not an accidental inconsistency.
- **Bounded loading**: `.limit(OPTIONS_LIMIT + 1)` = `.limit(201)` per type for the normal query (Locked decision 9 — enabling the truncation-flag computation above without a separate `COUNT` query), sliced to 200 before returning, plus the always-included linked value described above.
- **Search strategy**: none needed for MVP, matching §11's select-not-combobox recommendation — native `<select>` typeahead is the search mechanism at this scale.
- **Large-account behavior**: the explicit truncation flags are the whole mitigation for MVP — the UI (§9/§22) surfaces a visible, non-blocking note when a list is truncated, rather than silently showing an incomplete list with no signal; a "load more"/search upgrade is a clean, isolated future enhancement.
- **Caching/no-store policy**: `dashboardTasksNoStoreHeaders` (the exact same shared constant every other Calendar route already reuses) — matches the rest of the dashboard's "fetch fresh every time, no client cache library" convention (confirmed: no SWR/React Query dependency exists anywhere in this repo, verified directly via `package.json` and a repo-wide grep).
- **Loading/error states**: match the dialog's own loading/error convention (§16) — options fail to load → an inline error inside the dialog with Retry, not a page-level failure; the dialog remains otherwise usable (title/date/time/notes still work) even if options fail.
- **Can project and client options load together?** Yes — one request, `{projects, clients, projectsTruncated, clientsTruncated}`, rather than two separate round-trips, since both are needed at the same moment (dialog open) and both are cheap, narrow queries.

### One new read API endpoint is required — this milestone is not "UI-only" (correction, see §1/§5)

Every earlier or later reference in this report to the milestone being purely "UI-only," or to "zero API changes," refers only to the **existing** write/read Manual Event routes (`GET /api/calendar`, `POST`/`PATCH`/`DELETE /api/calendar/events[...]`) and the database/schema/RLS layer beneath them — all of which genuinely need zero changes. `GET /api/calendar/options` is a **new** route, requiring a new, small `lib/calendar/load-calendar-options.server.ts` repository module (modeled closely on `load-unscheduled-projects.server.ts`'s generic-client, `user_id`-scoped, no-store pattern) and its own route test file — this is real, if small and low-risk, backend work, not zero.

### When should options load?

**Lazily, only when the dialog first opens in a given session — not eagerly on Calendar page load.** Rationale: many Calendar visits never open Add/Edit at all (pure browsing/viewing), so eagerly fetching project/client options on every page load would be pure waste for that (likely common) case; the cost of a lazy fetch is one extra small request the first time a user opens the dialog, well within this app's existing "fetch on demand, no aggressive prefetching" convention (confirmed: the Calendar's own month data isn't prefetched for adjacent months either). In **edit mode**, the `includeProjectId`/`includeClientId` parameters are known immediately (from the event being edited), so the request can be issued the instant the dialog opens in edit mode, with no extra round-trip.

**Cached for the session** (a simple in-memory cache in whichever component owns the fetch, e.g. `WorkCalendarClient` or a small dedicated hook), **keyed by the `includeProjectId`/`includeClientId` pair actually requested** (since two different edit sessions may need two different always-included values) — a create-mode open (no include params) can reuse a previously-cached create-mode result; an edit-mode open for an event whose linked project/client isn't already present in a cached result needs its own fetch. **Must be invalidated/refetched** if a create/edit/delete has occurred that could plausibly have changed the set — in practice, this milestone doesn't create/edit/delete *projects* or *clients* themselves, only events, so the option data itself never goes stale from anything this milestone does; the only staleness source is a different browser tab/session archiving or deleting a project, which the normal "options fail gracefully, retry available" handling already covers without needing a subscription/realtime mechanism, matching the rest of the dashboard's no-realtime convention.

## 11. Select vs. searchable combobox decision (Step 8)

**Recommendation: native `<select>` for both Project and Client pickers.** Confirmed by a dedicated research pass across the whole `app/` tree:

- **Zero custom-combobox precedent exists anywhere in this repository.** No `@headlessui/react`, `cmdk`, `downshift`, `react-select`, or any hand-built `role="combobox"`/`aria-activedescendant`/typeahead-listbox implementation was found. The only `role="combobox"` in the entire app is the browser's own implicit ARIA role on native `<select>` elements (confirmed directly in `date-field.test.tsx`: `screen.getByRole("combobox", { name: "Choose the Month" })` — a real native `<select>`, not a custom widget).
- **Every existing dropdown in the dashboard — every one, without exception — is a plain, inline-styled native `<select>`.** Two small file-local wrapper components exist (`SelectField` in `project-update-review-card.tsx`, `FilterSelect` in `tasks-toolbar.tsx`, `ProjectPreviewMetricSelect` in `project-preview-presentation.tsx`) but none is exported/shared — each file independently re-implements the same shape. **No shared `Select` component exists in `app/components/dashboard/ui/`**, confirmed absent (re-confirmed this session, matching the original mapping's finding).
- **Scale evidence supports native `<select>` comfortably**: this milestone's own locked cap (200 per type, §10) is well within native `<select>`'s comfortable range — browser-native typeahead (type a letter, jump to the first match) handles list sizes in the hundreds without difficulty; a custom searchable combobox earns its complexity budget well above that, which the locked cap deliberately stays under.
- **Mobile behavior favors native `<select>` outright** given this specific codebase's demonstrated history: the read-only month view's own corrective pass (prior milestone) had to carefully re-engineer a custom mobile calendar picker's CSS to avoid clipping/duplicate-control bugs on small viewports. A native `<select>` sidesteps that entire risk class for free — mobile browsers render it as the OS's own full-screen picker, with zero custom responsive CSS/JS required.
- **Keyboard behavior**: native `<select>` is fully keyboard-operable with zero extra work (arrow keys, typeahead, Enter/Escape) — matching the exact trust this codebase already places in native selects elsewhere (`DateField`'s own month/year dropdowns handle 30+ years of options via `user.selectOptions` in tests, with no custom listbox).
- **Implementation complexity / testability**: a native `<select>` needs zero new accessibility infrastructure (focus management, `aria-activedescendant`, live-region announcements for filtered results) that this team has never built or tested before; a custom combobox would be a first-of-its-kind a11y surface for this one feature.
- **Future reuse**: if a shared `Select` wrapper is introduced as part of this milestone (a reasonable, small, additive step — see §28's file list), it should finally consolidate the three existing file-local duplicates (`SelectField`/`FilterSelect`/`ProjectPreviewMetricSelect`) into one `app/components/dashboard/ui/select.tsx`, rather than adding a **fourth** independent reimplementation of the same "labeled `<select>` with an options array" shape. This is optional polish, not required for this milestone's own correctness, but is a clean, low-risk, in-scope opportunity given the picker work is happening anyway.

**Not recommended for this milestone**: a custom accessible combobox/autocomplete. It would be justified only if the locked cap (200, §10) were raised substantially in the future (nothing in this codebase's evidence suggests that's imminent), and would introduce a first-of-its-kind accessibility surface with no existing pattern to build on or test against — directly conflicting with the "no cosmetic fixes that hide architectural problems" / "recommend the smallest correct shared primitive" spirit of this milestone's own rules.

**Empty-state / project-with-no-client / disabled-when-locked / truncated-list handling** (native `<select>`, all straightforward): a leading disabled placeholder option (`<option value="" disabled>No projects yet</option>` when the list is empty, or `<option value="">No project</option>` as the default unselected choice when projects exist — mirroring `project-meta-editor.tsx`'s existing "Not specified" disabled-option convention for a field with no assigned value); a `disabled` attribute on the Client `<select>` whenever a project is currently locking it (§9); and a small, visible, non-blocking note near the field when `projectsTruncated`/`clientsTruncated` is `true` (§22), satisfying "truncation must never be silent" without any new interactive-control complexity.

## 12. Create flow (Step 9)

1. User clicks the standalone **Add Event** action (Locked decision 2, §3/§4) — end/right-aligned, rendered by `WorkCalendarClient` above `CalendarToolbar`, never a `DayPicker`-button, never moving the page `H1`/subtitle into the client component.
2. `CalendarEventForm` opens inside `ResponsiveDialog` in **create mode**: Title empty, Date defaulted to the currently-selected day (`selectedDate`, Locked decision 1 — day-select only selects, it never opens a dialog on its own), Time/Notes empty, Project unselected (`<option value="">No project</option>`), Client unselected and **unlocked**.
3. Options load (§10) with no `includeProjectId`/`includeClientId` (nothing is linked yet). While loading, Project/Client selects render `disabled` with a loading affordance (§16/§22); Title/Date/Time/Notes remain interactive immediately — options loading never blocks the rest of the form.
4. **If the user selects a Project** (Correction 2, scenario 1 — create-mode-project-selected): the Client field immediately updates to that project's *current* `clientName` (from the already-loaded `CalendarProjectOption.clientName`, no extra round-trip) and **locks** (`disabled`, matching Locked decision 5's native-`<select>`-only-this-milestone framing — a disabled `<select>` is the lock affordance, not a separate read-only text swap). This is a pure client-side derivation from the already-fetched options payload.
5. **If the user later clears the Project** back to "No project" (Correction 2, scenario 4 — project-cleared): the Client field **unlocks** and *retains whatever client value was showing* (it does not silently reset to empty) — the user may then leave it, change it, or clear it independently.
6. Submit sends `POST /api/calendar/events` with `{title, eventDate, eventTime, notes, projectId, clientId}` — matching `CreateCalendarEventInputSchema`'s real field names exactly (§5; **never** `date`/`time` — those are display-layer/internal names only and must not appear in the actual request body) — exactly as today, **no new fields, no changed request shape**; the derived client-lock behavior is UI-only and the server independently re-derives/validates the project→client relationship via `validateCalendarEventLinks` regardless of what the client sent (§5/§9), so a locked Client selection is a UX convenience, not a trust boundary.
7. On success, the API returns the complete normalized `ManualCalendarEventItem` (§5) — no second fetch is needed to render the new event; it is merged directly into calendar state per the mutation reconciliation strategy (§15), which also increments `calendarDataVersionRef` (Correction 3).
8. Dialog closes; focus returns to the Add Event trigger, matching this codebase's existing dialog-focus-return convention (confirmed in `date-field.test.tsx`'s own "returns focus to the trigger" tests, §6).
9. No unsaved-change confirmation on close (Locked decision 6) — clicking outside/Escape/Cancel while fields are dirty discards silently, matching this dialog's overall low-friction design intent; this is a deliberate, explicit product decision, not an oversight.

## 13. Edit flow (Step 10)

1. User clicks the event's explicit **Edit** button (Locked decision 4 — no whole-card click; the card itself is not a button/link, only the Edit affordance is interactive for entering edit mode, avoiding the nested-interactive-element problem already avoided elsewhere in this codebase, §6/day-cell precedent).
2. `CalendarEventForm` opens inside `ResponsiveDialog` in **edit mode**, pre-filled from the event's already-known, already-normalized fields (no extra fetch needed for the form's own text/date/time/notes values — the event object the list already holds is complete, §5).
3. The options request is issued immediately with `includeProjectId=<event.projectId>` and `includeClientId=<event.clientId>` (when non-null) — guaranteeing the event's *currently-linked* project/client are present in the Project/Client `<select>` options even if the project is archived or either value falls outside the normal 200-item cap (§10). Until this resolves, Project/Client selects render `disabled` with a loading affordance showing the event's current text values (not blank) so the dialog never flashes an empty picker over a known value.
4. **Client-field behavior is governed by exactly the following four scenarios (Correction 2) — no others exist:**
   - **(a) Edit-mode, `projectChanged` is `false`.** The user's current Project value equals `initialProjectId` — either nothing about Project was touched, or it was touched and netted back to its original value (e.g. cleared then reselected, §9). On submit, the `PATCH` body **omits `projectId` and `clientId` entirely** (not merely re-sends the same values) — the event's originally-stored client relationship is preserved exactly as-is server-side, with zero risk of a client-side derivation accidentally overwriting a value the user never actually changed. This is the default, most common path and must be the one with the least risk of any client-derived overwrite.
   - **(b) Edit-mode, `projectChanged` is `true` and the new value is non-null.** The user's current Project selection genuinely differs from `initialProjectId` and is not empty — either a different project was selected, or a project was selected after having been cleared earlier in the same session (landing on a value that differs from the initial one; reselecting the *exact original* project after clearing nets `projectChanged` back to `false` and scenario (a) governs instead, §9). **Reselecting the already-selected project is also not a distinct action in this MVP** — a native `<select>` does not fire `onChange` when the user picks the value that's already selected, so there is no "refresh client from project" trigger to build. When this scenario applies: the Client field updates to **that project's current client** and (re-)locks (identical mechanism to create-mode, §12 step 4) — this discards/ignores any `clientChanged` state accumulated while Client was briefly independently editable during an intervening clear (§9). The `PATCH` body includes the new `projectId` **only** — it must **not** include a client-derived `clientId`. The server (`validateCalendarEventLinks`, §5/§9) remains the sole authority that derives and persists the client relationship; the PATCH response's own normalized `clientId`/`clientName` — not anything the client displayed or guessed — is what the mutation-reconciliation step (§15) splices into calendar state.
   - **(c) Edit-mode, `projectChanged` is `true` and the new value is `null`.** The user clears Project back to "No project" (differing from a non-null `initialProjectId`). The Client field **unlocks**, becomes independently editable, and `clientChanged` begins to apply — Client *retains* the event's current client value on unlock (does not reset to empty), exactly mirroring create-mode's clear behavior (§12 step 5). `PATCH` includes `projectId: null`. If `clientChanged` is `false` (Client left alone after unlocking), `clientId` is **omitted** from the `PATCH` entirely — the client value has not changed from the server's point of view, so it is not re-sent, and the server preserves the event's already-stored client exactly. If `clientChanged` is `true` (the user changed or cleared Client while it was unlocked), `clientId` is **included**, set to its new value or `null` (this mirrors §9 scenario 4 exactly).
   - **(d) Create-mode-project-selected** is not an edit-mode scenario — listed here only for completeness since §9 defines it alongside (a)-(c); see §12 step 4 for its full description. It is included so a single "four scenarios" cross-reference (used throughout §9/§12/§13/§22/§23) is unambiguous about covering both modes.
   
   **Dirty-tracking implementation note** (mirrors §9): **two independent value-comparison flags, `projectChanged`/`clientChanged` — never a single combined relationship-dirty boolean.** `projectChanged = currentProjectId !== initialProjectId` gates whether `PATCH` includes `projectId` at all — a pure equality check against the value captured when the dialog opened, not an interaction/"was touched" flag, so a clear-then-reselect-the-original-value nets back to `false`. `clientChanged = currentClientId !== initialClientId`, tracked and meaningful only while Client is independently editable (Project currently cleared, scenario (c)); it is discarded once Project is set again and re-locks Client (scenario (b)), so no stale independently-selected client value can ever leak into a `PATCH` alongside a `projectId`. Title/Date/Time/Notes are tracked and sent independently per their own per-field dirty comparison, exactly as today (§5).
5. Submit sends `PATCH /api/calendar/events/[id]`, where `[id]` is derived by `parseManualCalendarEventId(itemId)` (Correction 5, §5/§28) — the pure, fail-closed helper that requires the exact `event:` prefix and validates the UUID remainder, replacing any ad-hoc `.replace("event:", "")`/`.slice(6)`-style string manipulation. If parsing fails (should be structurally impossible given the discriminated union, §5, but the helper fails closed rather than assuming), the mutation is aborted client-side with a generic error rather than sending a malformed request.
6. On success, the API returns the complete normalized `ManualCalendarEventItem` — merged into calendar state via the mutation reconciliation strategy (§15), which increments `calendarDataVersionRef` before reconciling (Correction 3).
7. Dialog closes; focus returns to the Edit button that opened it — which remains present in the DOM, since a successful save updates the card in place rather than removing it (contrast with a successful Delete, §14 step 6, where that button is guaranteed gone). No unsaved-change confirmation on close (Locked decision 6), identical to create mode.
8. **Delete lives inside this same dialog, edit-mode only.** The form's own action row includes an explicit Delete control alongside Save/Cancel; activating it begins the inline two-step confirm entirely within this dialog (§14) — never a separate control on the agenda card, and never present at all when the dialog is open in create mode, since an unsaved event has nothing to delete.

## 14. Delete flow (Step 11)

**One architecture, locked**: Delete exists **only** inside `AddEditCalendarEventDialog`, in **edit mode** — it is reached by clicking the event's Edit button (§13 step 1), then activating Delete inside the resulting dialog/form's own action row. There is **no** separate Delete control on `SelectedDayAgenda`/`CalendarAgendaItem` (§3/§4), no nested delete dialog, and Delete is not available at all while the dialog is open in create mode (there is nothing to delete yet). `ProjectDeadlineRow` remains fully read-only throughout, unaffected by any of this (explicit out-of-scope, §3).

1. From inside the edit-mode dialog, the user clicks Delete — an explicit control in `CalendarEventForm`'s action row, alongside Save/Cancel (§8), separate from Edit (which is how the dialog was reached in the first place) and never combined into a single overloaded control.
2. **Inline two-step delete confirmation** (Locked decision 8): the Delete control transforms in place into a "Confirm delete?" affordance (e.g. the button's own label/style swaps to a confirm state, with a Cancel escape hatch alongside it) — entirely within the same dialog/form's own action row. No second, nested dialog/overlay is opened for confirmation — this is a single, lightweight, inline state change, not a dialog-over-a-dialog. This mirrors the existing `TaskDeleteModals` precedent's *intent* (a deliberate, momentary "are you sure" step before an irreversible action) but implemented as an inline control-state change rather than as its own modal, exactly matching `ResponsiveDialog`'s own "explicitly left to the caller" note (§7) that this specific sub-flow deliberately avoids composing a second overlay.
3. On confirm, `DELETE /api/calendar/events/[id]` is sent, with `[id]` derived via `parseManualCalendarEventId(itemId)` exactly as in the edit flow's own PATCH construction (Correction 5, §13 step 5) — the same fail-closed helper is used for both PATCH and DELETE, so there is exactly one place in the codebase that ever turns a `CalendarItem.id` into the raw UUID the API expects.
4. **Success response is `{success: true, alreadyDeleted: boolean}` (§5) — never described as bodyless or success-only.** Both outcomes are treated as a successful UI result and handled identically: `alreadyDeleted: false` means this request performed the soft-delete; `alreadyDeleted: true` means the event was already soft-deleted (e.g., by another tab/session racing this one) and this request was a no-op confirmation of that fact — the UI does not distinguish between the two with different messaging, since from this dialog's point of view the end state (event gone) is the same either way.
5. On either outcome, the dialog closes and the deleted event is removed from calendar state via the mutation reconciliation strategy (§15): `calendarDataVersionRef` is incremented *before* reconciling (Correction 3), and the removal is applied against whatever range is *currently* loaded — not necessarily the range that was loaded when the dialog was first opened, since the dialog may have been open long enough for the visible range to change (§15's general reconciliation contract, uniform across create/edit/delete).
6. **Focus return, corrected**: unlike a successful save (§13 step 7), a successful delete does **not** return focus to the Edit button that opened the dialog — that button's card was just removed from the list by the same mutation reconciliation that closes the dialog (§15), so the button is guaranteed to no longer be connected to the document by the time focus would return. The dialog does not attempt to focus a detached element. Instead: it checks whether the originating trigger is still connected to the document; since it never is after a successful delete, focus falls back to the stable **Add Event** button, which always exists regardless of how many events are on the selected day. If that button is unexpectedly unavailable too (a defensive-only edge case with no known trigger), focus falls back to the `SelectedDayAgenda` heading (`<h2>`) via a programmatic ref with `tabIndex={-1}`, so focus always lands somewhere sensible and never silently vanishes into the document body.
7. If the currently-selected day's item list becomes empty as a result, the day view shows the same empty state as any day with zero items (§17/§22) — no special-cased "you just deleted the last one" messaging.
8. No separate confirmation dialog beyond the inline two-step, no toast-undo — consistent with Locked decision 8's explicit inline-two-step (not modal, not undo-snackbar) design.

## 15. Mutation reconciliation strategy (Step 12) — Correction 3

**This section supersedes an earlier, incorrect conclusion from a prior pass of this mapping**, which stated "no additional request-version counter is needed beyond the existing `requestIdRef`/`requestKey` pair." That conclusion did not account for the specific race a mutation introduces: `requestIdRef`/`requestKey` alone protect against *stale GETs* (an in-flight fetch superseded by a newer one, or a fetch that resolves after the component's `requestKey` — e.g. visible month/date range — has moved on) but say nothing about a GET that was in flight *before* a mutation completed and resolves *after* it, carrying data that predates the mutation. Without an additional signal, such a stale-but-otherwise-"current" GET can silently overwrite a just-applied optimistic mutation result with older data.

### The corrected architecture: `calendarDataVersionRef`

- `WorkCalendarClient` owns one additional `useRef<number>` — `calendarDataVersionRef` — initialized to `0`, monotonically incremented, never reset.
- **Every GET** (the existing range-fetch, guarded today by `requestIdRef`/`requestKey`, §2) additionally captures `calendarDataVersionRef.current` into a local variable **at the moment the request is issued** (not when it resolves).
- **A GET's result is committed to state only if all three of the following are still true when it resolves**: its own `requestId` still matches `requestIdRef.current` (existing guard, unchanged), its own `requestKey` still matches the currently-relevant key (existing guard, unchanged — e.g. the visible range hasn't changed), **and** its captured data-version still equals `calendarDataVersionRef.current` (new guard, Correction 3). If any of the three has moved on, the GET's result is discarded — it is definitionally stale, either because a newer fetch superseded it, the visible range changed, or a mutation committed while it was in flight.
- **Every successful mutation (create/edit/delete, §12/§13/§14) increments `calendarDataVersionRef.current` *before* reconciling its own optimistic update into state** — this ordering matters: it guarantees that any GET whose captured version predates the mutation is unambiguously identifiable as stale by the time the mutation's own reconciliation runs, closing the exact race the prior "no additional counter needed" conclusion missed.
- **Reconciliation is applied against the CURRENT range, not the range that was loaded at dialog-open time.** A mutation's dialog may have been open long enough (or the user may act fast enough on a slow connection) that the visible date range changed while it was open. On mutation success, the reconciliation logic re-checks what range is *currently* the committed, successful one (i.e., whatever `WorkCalendarClient`'s own state currently reflects as loaded) and applies the create/update/delete against *that* range's item list — never against a stale closed-over range captured when the dialog first opened.
- **If, at the moment a mutation succeeds, there is no current successful range in state at all** (e.g. the initial load is still in flight, failed, or was itself superseded and a fresh one hasn't landed yet) — rather than attempting to splice into a range that doesn't reliably exist, the mutation instead **triggers a fresh load for the current range** after incrementing the data version. This guarantees the UI never ends up in an inconsistent, partially-spliced state and always converges to a real server-confirmed view shortly after the mutation completes.

### Why this is Option A (not a hybrid, not Option C) plus a data-version guard

An earlier pass of this mapping considered "Option A" (splice the mutation's known result directly into the currently-held item list, no refetch) against "Option C" (always trigger a full refetch after every mutation, no local splicing) and a hybrid of the two. **The corrected recommendation is Option A — direct splicing — augmented with the `calendarDataVersionRef` guard above**, not a hybrid and not Option C as a default: a full refetch after every single create/edit/delete would be wasteful (the API already returns everything needed to update state directly, §5) and would introduce a visible flash/loading state on every mutation that direct splicing avoids. Option C is used **only** as the narrow fallback described above, for the specific case where no current successful range exists to splice into — not as the general strategy.

### Concrete sequencing example (the race this closes)

1. `calendarDataVersionRef.current` is `5`. A background GET for the visible range is issued, capturing version `5`.
2. Before that GET resolves, the user finishes editing an event; `PATCH` succeeds. Per the rule above, `calendarDataVersionRef.current` is incremented to `6` *before* the edit's own reconciliation splices the updated event into the current range's state.
3. The GET from step 1 now resolves, carrying data that reflects the pre-edit state (it was issued before the edit committed). Its captured version (`5`) no longer matches `calendarDataVersionRef.current` (`6`) — per the corrected commit rule, its result is discarded rather than committed, so the just-applied edit is never silently clobbered by the stale GET.

Without step 3's guard, the stale GET's `requestId`/`requestKey` could easily still both be "current" (nothing about the range or request identity changed — only a mutation happened elsewhere), which is precisely why `requestIdRef`/`requestKey` alone were insufficient and the additional monotonic version is required.

## 16. Desktop UX (Step 13)

**One architecture, not two** (Locked decision 7): the dialog is a `ResponsiveDialog`, and on desktop that primitive renders as a **centered modal** — an overlay dimming the page behind it, the dialog panel centered in the viewport, focus trapped inside (§7/§19), Escape/outside-click closing without confirmation (Locked decision 6). There is no separate "desktop dialog" and "mobile dialog" component — `ResponsiveDialog` is the single implementation whose *rendering strategy* (centered modal vs. bottom sheet, §17) switches on viewport, exactly as the name implies; `CalendarEventForm`'s own field layout/logic is identical regardless of which chrome it's rendered inside.

- **Layout**: Title full-width; Date/Time as a two-column row where width allows (matching the compact spacing already used elsewhere in the dashboard's form-heavy surfaces); Project/Client as a second two-column row; Notes full-width, multi-line.
- **Loading state while options load** (§10/§12): Project/Client `<select>` elements render `disabled` with a small inline spinner/label ("Loading…") rather than an empty option list — never an interactive-but-empty dropdown.
- **Truncation note** (§10/§11/§22): a small, non-blocking inline note beneath the affected `<select>` when `projectsTruncated`/`clientsTruncated` is `true`.
- **Submit/Cancel row**: bottom-right-aligned (matching the general dashboard convention of primary-action-bottom-right), Submit disabled while a mutation is in flight (no double-submit), with a small inline spinner replacing the button's label text during submission — mirroring `DateField`'s own "Saving..." trigger-label convention (§6) rather than inventing a new busy-affordance pattern.
- **Nested DatePicker behavior on desktop**: opening the Date field's popover from inside the centered modal is governed entirely by the nested-overlay contract described in §18 — not by z-index alone.

## 17. Mobile UX (Step 14)

Per Locked decision 7, mobile renders the same `ResponsiveDialog`/`CalendarEventForm` pair as a **bottom sheet** — anchored to the bottom edge of the viewport, sliding up, occupying up to a bounded maximum height with internal scrolling for content overflow (Notes being the field most likely to push height), rather than the desktop centered-modal treatment. This directly reuses the lesson already learned and documented in this codebase's own prior corrective pass on the read-only month view's mobile compact selector (`calendar-compact-selector.test.tsx`, confirmed in this session's context): avoid fixed pixel widths/heights that don't respond to real small-viewport constraints, and verify with real manual QA at 320/360/375/390/400px rather than trusting jsdom's non-layout test environment alone (that prior corrective pass's own tests explicitly note jsdom "does not perform real layout/paint" and that manual QA "remains required" — the same caveat applies here).

- **Field layout collapses to a single column** on narrow viewports (no two-column Date/Time or Project/Client rows) — matching the same container-based, non-fixed-width responsive approach already proven in `CalendarCompactSelector`.
- **Native `<select>` on mobile** renders as the OS's own full-screen picker (§11) — this is the primary reason native `<select>` was recommended over a custom combobox: it sidesteps the exact class of mobile clipping/overflow bug the prior corrective pass had to fix by hand for the compact date-grid.
- **The Date field's own popover (`DatePickerPopover`) inside a mobile bottom sheet** is the single hardest case in this whole feature for the nested-overlay problem (§18) — a bottom sheet already occupies much of a small viewport, and a full centered/anchored date-picker popover opening on top of it has the least room to avoid visual collision; the nested-overlay-host contract (§18) is what keeps this workable without ad-hoc per-viewport z-index tuning. This is precisely why the host is placed as a **sibling of the sheet's own scrollable content region, not nested inside it** (§7) — a popover portaled inside the sheet's own scroll/overflow handling would be clipped by it exactly as it would be clipped by the desktop panel's `overflow-y: auto`, and a mobile bottom sheet is the tightest-fitting, least-forgiving case for that failure mode to actually surface.
- **Sticky submit/cancel row**: pinned to the bottom of the sheet (below the scrollable field area) so they remain reachable without scrolling to the sheet's end, regardless of Notes length.
- **No unsaved-change confirmation** (Locked decision 6) applies identically on mobile — swiping/tapping the scrim closes without a confirm step, consistent with desktop.

## 18. Nested DatePicker / dialog resolution (Step 15) — Correction 4

**An earlier pass of this mapping recommended a single additive z-index token as the fix for the Date field's popover appearing inside the Add/Edit Event dialog.** That recommendation is corrected here: **z-index alone is insufficient.** Raising `DatePickerPopover`'s stacking context above `ResponsiveDialog`'s own overlay only solves the *visual* layering — it does nothing about the two independent event-handling systems that would otherwise both be live at once: `ResponsiveDialog`'s own Escape-key handler, outside-click handler, and focus trap (§7), and `DatePickerPopover`'s own **already-existing, independent** Escape/outside-click/focus-return system (confirmed in §6: `DatePickerPopover` portals directly to `document.body` and owns its own complete dismissal logic, entirely unaware that it might ever be rendered inside another dialog). With z-index as the only change, pressing Escape while the nested date popover is open is ambiguous — it could close just the popover, just the outer dialog, or (worst case) both at once, depending on handler registration order, which is exactly the kind of subtle, hard-to-test interaction bug this milestone must not ship.

### The corrected architecture: a real nested-overlay contract

1. **`ResponsiveDialog` provides a nested-overlay host and a small React context** (e.g. `NestedOverlayContext`, exposing something like `{ activeNestedOverlayId: string | null, registerNestedOverlay(id): void, unregisterNestedOverlay(id): void }`) to its descendants. The "host" is a DOM node/portal target rendered **as a sibling of the dialog panel's own scrollable content region, inside the same portal root** (§7) — not a descendant of the panel — that a nested overlay can portal into instead of portaling all the way to `document.body`. This sibling placement (not "somewhere inside the panel") is what prevents the nested popover from being clipped by the panel's own `overflow-y: auto`, border-radius, or (on mobile) the bottom sheet's own scroll handling — a clipping failure mode that z-index cannot fix, since z-index only controls paint order within a stacking context, not whether an ancestor's `overflow` clips a descendant. The host paints above the panel.
2. **`DatePickerPopover` gains an optional integration path**: when rendered inside a `ResponsiveDialog` (detected via the context being present — `useContext(NestedOverlayContext)` returning non-null, not a boolean prop the caller must remember to pass), it portals into the host instead of `document.body`, and calls `registerNestedOverlay(ownId)` on open / `unregisterNestedOverlay(ownId)` on close.
3. **While registered, `DatePickerPopover` continues to own its dismissal and focus behavior exactly as it always has** — its own Escape handler, its own outside-click handler (scoped to its own popover boundary), its own focus trap/return-to-trigger logic (§6's existing, already-tested behavior, unchanged). This is the key design choice: the nested popover is not rearchitected, only *made aware* it has an outer dialog to coordinate with.
4. **`ResponsiveDialog` suspends its own Escape handler, outside-click handler, and focus trap while `activeNestedOverlayId` is non-null.** Concretely: its Escape listener checks the context's `activeNestedOverlayId` before acting and no-ops if a nested overlay is active (letting the nested popover's own listener — which fires first/deeper in the DOM, or is checked first depending on implementation — be the one that actually handles the keypress); its outside-click handler similarly ignores clicks that land inside the registered nested overlay's host region; its focus trap does not attempt to re-capture focus that the nested popover has intentionally moved to its own internal elements (e.g. a day cell, per `DateField`'s own keyboard-flow tests, §6).
5. **The outer focus trap must ignore already-`defaultPrevented` keyboard events.** Because both systems could in principle observe the same native keyboard event during the brief moment a nested overlay is opening/closing, the outer trap explicitly checks `event.defaultPrevented` and no-ops if the nested popover's own handler already claimed the event — a small, explicit contract rather than relying on listener-registration-order accidents.
6. **Existing standalone `DateField`/`DeadlineField` callers outside any `ResponsiveDialog`** (e.g. wherever a deadline date is edited directly on a project card today, outside this Calendar feature) **are completely unaffected**: `NestedOverlayContext` is simply absent for them (no `ResponsiveDialog` ancestor providing it), so `DatePickerPopover`'s `useContext` call returns `null`/undefined and it falls back to its current, already-shipped, already-tested `document.body`-portal behavior exactly as today — zero behavior change for every existing caller.
7. **The z-index token from the earlier recommendation is retained, but only as a supplementary, explicitly-not-sufficient safeguard** — a defensive layer in case some future overlay is composed in a way the context-based contract doesn't yet cover, not the primary mechanism. It costs nothing to keep and removes one class of purely-visual glitch, but this report no longer frames it as "the fix."

### Why this is the smallest correct fix, not a `DatePickerPopover` fork

The alternative considered and rejected: forking `DatePickerPopover` into a "nested-aware" variant used only inside Calendar's dialog. Rejected because it would create two parallel implementations of the same picker to keep in sync forever, for a difference (awareness of an outer dialog) that is naturally expressed as an optional integration path via context rather than a structural fork. The context-based approach keeps exactly one `DatePickerPopover` implementation, with one new optional behavior that no-ops to today's exact behavior when there's no outer `ResponsiveDialog`.

## 19. Accessibility (Step 16)

- **Focus trap**: `ResponsiveDialog` traps focus within its own panel while open, exactly as `DatePickerPopover`/`DateField` already do today (§6) — **with the Correction 4 amendment (§18)**: the trap suspends itself while a nested overlay (the Date field's popover) is registered active, and ignores any keyboard event the nested overlay's own handler has already called `preventDefault()` on, so the two focus systems never fight over the same keypress.
- **Labeling**: every field has a real, programmatically-associated `<label>` (native `<select>`/`<input>` labeling, matching `DateField`'s own `getByLabelText` testing convention, §6) — no placeholder-as-label anti-pattern.
- **Dialog role/name**: `ResponsiveDialog` renders `role="dialog"` with an accessible name (`aria-labelledby` pointing at the form's own heading — "Add event"/"Edit event") — matching `DateField`'s own `getByRole("dialog", { name: ... })` precedent (§6).
- **Live-region announcement on save**: mirrors `DateField`'s existing "Selected [date]" visually-hidden live-region pattern (§6) — a brief, visually-hidden confirmation announced on successful create/edit/delete, so a screen-reader user gets non-visual confirmation the action completed, without needing a visible toast.
- **Delete's inline two-step confirm** (§14/Locked decision 8) must itself be accessible without a dialog: the transformed "Confirm delete?" control needs its own clear accessible name change (not just a visual style swap) so a screen-reader user perceives the state change, and the Cancel escape-hatch must be independently reachable by keyboard.
- **Keyboard-only flow end to end**: Add Event trigger → dialog opens with focus moved to the first field → Tab through Title/Date/Time/Project/Client/Notes → Date field's popover is itself fully keyboard-operable exactly as already tested (`date-field.test.tsx`'s "full keyboard-only selection flow" test, confirmed in this session's context) and, per Correction 4, that keyboard operability is now guaranteed to work correctly *nested* inside the outer dialog, not just standalone → Submit → focus returns to the trigger that opened the dialog, matching the existing, already-tested convention.
- **Delete's focus-return fallback chain** (corrected, §7/§14): Save/Cancel always return focus to a still-connected trigger (the card is never removed by those paths). A successful Delete is the one path whose trigger (the Edit button) is guaranteed removed from the DOM by the time focus would return — the dialog must never attempt to focus a detached element. The chain is: originating trigger if still connected (never true after a successful delete, but checked defensively) → the stable Add Event button (always present) → the `SelectedDayAgenda` heading via a programmatic ref with `tabIndex={-1}` (last-resort fallback) — so a screen-reader/keyboard user's focus never silently drops to `<body>`.
- **Truncation note accessibility** (§10/§16/§22): the inline "list truncated" note is programmatically associated with its `<select>` (e.g. `aria-describedby`), not a purely visual-only cue.

## 20. Security (Step 17)

- **Existing write endpoints (`POST`/`PATCH`/`DELETE /api/calendar/events[...]`) need zero security-relevant changes** — ownership scoping (`user_id`), the `validateCalendarEventLinks`/`enforce_calendar_event_relationship_integrity` server-side re-derivation of the project→client relationship (§5/§9), and RLS all remain exactly as they are today. The client-side "locked" Client field (§9/§12/§13) is a UX affordance only; it is never trusted as the source of truth server-side.
- **`GET /api/calendar/options` is a new surface and needs its own explicit ownership validation** (§10/§5): the base project/client lists are already scoped by `.eq("user_id", userId)`, matching every existing project/client query in this codebase. The **new** attack surface is the `includeProjectId`/`includeClientId` query parameters — a caller could pass an arbitrary UUID hoping to learn whether it exists or belongs to another user. Both parameters must be independently re-validated with the same `.eq("id", ...).eq("user_id", userId)` ownership check used everywhere else (mirroring `validateCalendarEventLinks`'s own pattern), and an id that fails that check is **silently omitted** from the response — never surfaced as a distinct "not found" vs. "not yours" error, which would leak existence information about ids the requesting user doesn't own.
- **`parseManualCalendarEventId` (Correction 5, §5/§13/§14) is itself a small but real security-relevant boundary**: it fails closed on anything that isn't an exact `event:` prefix followed by a syntactically valid UUID, so a malformed or unexpected `itemId` (e.g. a `project:` id accidentally routed into the event-mutation path, or a manipulated client-side value) can never reach the PATCH/DELETE URL construction as raw, unvalidated string content. This doesn't replace server-side ownership checks (the API routes still independently verify the resolved UUID belongs to the requesting user) — it prevents a class of client-side request-construction bugs from ever producing a malformed or cross-entity request in the first place.
- **No new secrets, no new third-party calls, no new client-side storage of sensitive data** — this milestone introduces one new read route and client-side form/dialog logic; the trust boundary shape of the feature is unchanged from today.

## 21. Performance (Step 18)

- **`GET /api/calendar/options` is a small, bounded, `.limit(OPTIONS_LIMIT + 1)` = `.limit(201)`-per-type query** (§10 — the extra row is how `projectsTruncated`/`clientsTruncated` are computed without a separate, more expensive exact-`COUNT` query; the response itself is sliced back down to 200 normal items), issued lazily (only when the Add/Edit dialog first opens, not on every Calendar page load) and cached for the session keyed by the `includeProjectId`/`includeClientId` pair actually requested (§10) — the realistic steady-state cost is at most one or two extra small requests per Calendar session, not a query that scales with calendar browsing.
- **The 200-per-type cap (Locked decision 9) is a deliberate, explicit product decision**, not an inferred default — it replaces an earlier draft's informal reference to the unrelated `load-unscheduled-projects.server.ts` panel's own `50`-item precedent (§10), which was never validated against this feature's actual needs and belonged to a differently-scoped, differently-filtered query.
- **No pagination, no infinite scroll, no incremental loading** for options this milestone — native `<select>` at a 200-item cap is well within comfortable rendering/typeahead performance for every browser this app supports (§11); a future increase in the cap would be the trigger to revisit this, not something to build defensively now.
- **Mutation reconciliation (§15) is O(n) per mutation, not O(1)** — an immutable add/replace/remove over the currently-held `CalendarItem[]` array necessarily copies the array, so it is linear in the number of items currently held for the range, not constant-time; this report's own earlier "O(1)" framing was imprecise and is corrected here. In practice this is a non-issue at this feature's realistic scale (a single visible date range's worth of calendar items — nowhere near, for example, the 200-item options cap of §10/§21), so no batching/memoization work is warranted, but the complexity should be described correctly. This is never a refetch except in the narrow fallback case (no current successful range) where a single fresh load is triggered — that fallback path's cost is the GET path's own existing, unchanged performance characteristics.
- **No new polling, no new realtime subscription** — this milestone does not introduce any background refresh mechanism; staleness from another tab/session is handled by the existing manual-refetch-on-range-change behavior, unchanged.

## 22. Error / loading / edge-case states (Step 19)

| Scenario | Behavior |
|---|---|
| Options request fails (network/server error) | Inline error inside the dialog with a Retry action; Title/Date/Time/Notes remain usable; Project/Client remain disabled until a retry succeeds (§10/§16). |
| Options request in flight | Project/Client `<select>` render `disabled` with a loading affordance; in edit mode, the event's current project/client text is shown (not blank) while disabled (§13). |
| `projectsTruncated`/`clientsTruncated` is `true` | A small, non-blocking, `aria-describedby`-linked note beneath the affected `<select>` — never silent (Locked decision 9, §10/§16/§19). |
| Currently-linked project/client falls outside the normal 200-item window | Always present in the options response regardless, via `includeProjectId`/`includeClientId` (§10) — never missing from the edit-mode dropdown, never silently dropped. |
| Currently-linked project is archived | Included via `includeProjectId` with `isArchived: true`; rendered with a clear archived affix/label in the `<select>` option text, remains selectable (it's already selected) but is excluded from the "new selection" active project set otherwise (§9/§10). |
| Create-mode: Project selected | Client field auto-populates with that project's current client and locks (§9/§12, Correction 2 scenario 1). |
| Edit-mode: relationship untouched | `PATCH` omits `projectId`/`clientId` entirely; server preserves the event's stored relationship as-is (§9/§13, Correction 2 scenario 2). |
| Edit-mode: `projectChanged` is `true`, new value non-null | Client auto-populates with the new project's current client and locks, discarding any `clientChanged` state accumulated during an intervening clear; `PATCH` includes `projectId` **only** (never a client-derived `clientId`) — the server derives/validates and the PATCH response's own `clientId`/`clientName` is what gets reconciled into state (§9/§13, scenario (b)). Reselecting the already-selected project is a no-op (native `<select>` doesn't fire `onChange`), not a distinct "project changed" event. |
| Project cleared (create or edit) | Client unlocks and retains its current value; user may leave/change/clear it independently. `PATCH` includes `clientId` only if `clientChanged` is `true` (Client itself separately changed while unlocked) — otherwise `clientChanged` is `false` and `clientId` is omitted, preserving the event's stored client (§9/§12/§13, scenario (c)/scenario 4). |
| Project cleared, then a different project selected in the same session | Client re-locks to the newly-selected project's current client; any `clientChanged` value from the intervening unlocked period is discarded — `PATCH` sends `projectId` only, never the independently-selected `clientId` (§9, "selecting a new project after clearing it"). |
| Mutation succeeds, no current successful range in state | A fresh load for the current range is triggered after incrementing `calendarDataVersionRef`, rather than attempting to splice into a range that doesn't reliably exist (§15, Correction 3). |
| A GET resolves whose captured data version no longer matches `calendarDataVersionRef.current` | Discarded, never committed to state — regardless of `requestId`/`requestKey` still matching (§15, Correction 3). |
| `itemId` fails `parseManualCalendarEventId` validation | Mutation aborted client-side with a generic error before any PATCH/DELETE request is sent (§5/§13/§14, Correction 5). |
| Delete | Reached only from inside `AddEditCalendarEventDialog` in edit mode (never a control on the agenda card, never available in create mode); confirmed via an inline two-step (confirm/cancel in place within the dialog's own action row), no separate modal (§14, Locked decision 8). |
| `DELETE` succeeds with `alreadyDeleted: true` (already removed elsewhere, e.g. another tab) | Treated as an equally successful UI outcome to `alreadyDeleted: false` — dialog closes, event removed from local state identically either way (§5/§14). |
| Dialog closed with unsaved changes (Escape, outside click, Cancel) | Discards silently, no confirmation prompt, on both desktop and mobile (§16/§17, Locked decision 6). |
| Day selection | Selects the day only — never opens the Add/Edit dialog as a side effect (§12, Locked decision 1). |
| Empty day (zero items, including after a delete) | Standard empty-day state, no special "just deleted" messaging (§14). |

## 24. Recommended production architecture (Step 21)

- **API surface**: the three existing Manual Event write/read routes, unchanged, **plus one new route**, `GET /api/calendar/options` (§10/§20) — this milestone is **primarily a UI/client-state build, plus one small, narrow, new read endpoint**; it is not, and this report no longer describes it as, a "UI-only, zero API changes" milestone.
- **Shared dialog primitive**: `ResponsiveDialog` (§7), newly introducing a nested-overlay host/context responsibility (§18/Correction 4) alongside its original centered-modal/bottom-sheet, focus-trap, and Escape/outside-click responsibilities — consolidating what were nine independently hand-rolled dialog implementations (§6) onto one primitive, of which this milestone's own Add/Edit/(inline-delete-confirm) dialog is the first concrete adopter.
- **Form component**: `CalendarEventForm`, rendered inside `ResponsiveDialog`, consuming `CalendarProjectOption[]`/`CalendarClientOption[]` (§10) fetched via a small dedicated loader (e.g. a `useCalendarOptions` hook or equivalent, owned by `WorkCalendarClient` or the form itself) rather than any ad-hoc inline fetch.
- **Mutation reconciliation**: Option A (direct splice of the API's returned normalized item into current state) **augmented with the `calendarDataVersionRef` monotonic guard** (§15/Correction 3) — not a hybrid of splice-and-refetch, and not a refetch-every-time strategy; the fallback fresh-load path exists only for the narrow no-current-range case.
- **Nested date picker**: `DatePickerPopover`'s existing, unmodified dismissal/focus system, made nested-overlay-aware via an opt-in context integration (§18/Correction 4) — not a fork, not a z-index-only fix (z-index retained only as a supplementary safeguard). The overlay host it portals into is a DOM sibling of the dialog panel's own scrollable content, inside the same portal root, not a descendant of the panel (§7) — this is what actually prevents clipping, independent of z-index.
- **Event id resolution**: `parseManualCalendarEventId` (§5/§13/§14/Correction 5), the single, pure, fail-closed helper used everywhere a `CalendarItem.id` must become the raw UUID the write API expects.
- **State ownership**: `WorkCalendarClient` remains the single owner of `selectedDate`, the range-fetch lifecycle (`requestIdRef`/`requestKey`), and now additionally `calendarDataVersionRef` — no new top-level state owner is introduced; the dialog/form are controlled, stateless-between-opens consumers of callbacks it provides.

## 26. Phased implementation plan (Step 23)

**Phase A — Shared dialog primitive foundation**
Build `ResponsiveDialog` (§7) including its nested-overlay host and `NestedOverlayContext` (§18/Correction 4) from the start — not bolted on later, since retrofitting the nested-overlay contract onto an already-integrated dialog would touch more surface than building it in from the beginning. No consumer beyond a minimal smoke test yet.

**Phase B — Options data**
Build `GET /api/calendar/options` (§10/§20): the full `CalendarProjectOption`/`CalendarClientOption` shapes, `includeProjectId`/`includeClientId` with ownership validation (fetched separately and appended/deduplicated after the normal query is sliced), `.limit(OPTIONS_LIMIT + 1)` (201) per type with a slice-to-200 and length-comparison to compute `projectsTruncated`/`clientsTruncated` accurately without a separate exact-count query — the complete contract, not an `{id,title}`-only placeholder later widened.

**Phase C — Add/Edit form, including Delete**
Build `AddEditCalendarEventDialog` and `CalendarEventForm` and its field subcomponents against Phase A + Phase B's real contracts: `CalendarEventDateField` integrating with the nested-overlay context (a real integration — registering/unregistering, coordinating dismissal — not "add one z-index prop" as an earlier draft of this plan understated it); `CalendarEventProjectField`/`CalendarEventClientField` implementing the full four-scenario Client-lock behavior via two independent value-comparison flags, `projectChanged`/`clientChanged` (§9) — not a single combined relationship-dirty boolean — including the "no reselect trigger" rule and the "clientChanged is discarded once Project re-locks Client" rule; `parse-manual-calendar-event-id.ts` (Correction 5) plus its pure unit tests, used by `lib/calendar/mutate-calendar-event.client.ts`'s PATCH/DELETE construction (Correction 7); and the form's own Delete control — edit-mode only, inline two-step confirm within the same action row, handling both `alreadyDeleted` outcomes identically (§14) — since Delete is owned entirely by this form/dialog, not by the item cards.

**Phase D — Wiring, mutation reconciliation, and the Add Event trigger**
Wire `WorkCalendarClient`'s new `calendarDataVersionRef` (Correction 3) into both the existing GET path (capture-at-issue, commit-only-if-current) and every mutation path (increment-before-reconcile, reconcile-against-current-range, fresh-load fallback); add the standalone Add Event trigger (Locked decision 2) and wire the explicit Edit control (Locked decision 4) into the item cards. Delete's inline two-step confirm (Locked decision 8) was already built in Phase C, inside `CalendarEventForm` — Phase D does not add any Delete-related control to the item cards.

**Key risks carried into this phased plan**:
- The data-version guard (Phase D) is the phase most likely to surface subtle test-ordering/timing bugs — it requires deliberately-sequenced, deferred-promise test fixtures (§23) to actually exercise the race it closes; get this wrong and the guard's own correctness is unverifiable, not just the feature's.
- The nested-overlay contract (Phase A/C) is the second-highest-risk item — six explicit test cases are required (§23) precisely because "it looks right visually" is not sufficient evidence the Escape/focus/outside-click coordination is actually correct.
- Both risks were understated in an earlier draft of this plan (the data-version guard was previously omitted as unnecessary; the nested-overlay work was previously described as a one-line z-index change) — this corrected plan's higher time estimate (§29) reflects that these are genuine engineering risk items, not polish.

## 27. Parallel execution plan (Step 24)

With two engineers, Phase A (dialog primitive) and Phase B (options endpoint) have no interdependency and can proceed fully in parallel — one engineer owns `ResponsiveDialog` + nested-overlay contract, the other owns the options route + its repository module and tests. Phase C (form) depends on both completing (it consumes the dialog's nested-overlay context and the options endpoint's real response shape), so it is the first point of convergence; splitting Phase C itself further (one engineer on `CalendarEventDateField`'s nested-overlay integration, the other on `CalendarEventProjectField`/`CalendarEventClientField`'s Correction 2 logic plus `parseManualCalendarEventId`) is reasonable once Phase C starts. Phase D (mutation reconciliation + wiring) is best done by a single engineer with full context on both the existing `requestIdRef`/`requestKey` guard and the new `calendarDataVersionRef` addition, to avoid the exact kind of two-systems-not-coordinating bug this corrective pass had to fix conceptually in §15/§18.
