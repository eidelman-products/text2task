## 5. Final table schema

`public.authenticated_product_events` (migration `202608030001`):

```sql
create table if not exists public.authenticated_product_events (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  event_name text not null,
  route text not null,
  entity_type text null,
  entity_id text null,
  idempotency_key text null,
  created_at timestamptz not null default now(),

  constraint authenticated_product_events_route_length_check
    check (char_length(route) <= 300),
  constraint authenticated_product_events_entity_type_check
    check (entity_type is null or entity_type in ('project', 'calendar_event', 'calendar_day')),
  constraint authenticated_product_events_entity_id_length_check
    check (entity_id is null or char_length(entity_id) <= 64),
  constraint authenticated_product_events_entity_consistency_check
    check (
      (entity_type is null and entity_id is null)
      or (entity_type = 'calendar_day' and entity_id ~ '^\d{4}-\d{2}-\d{2}$')
      or (
        entity_type in ('project', 'calendar_event')
        and entity_id is not null
        and entity_id ~* '^[0-9a-f]{8}-[0-9a-f]{4}-[1-5][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$'
      )
    )
);
```

No `metadata`/`jsonb` column, no free-form content column, no `updated_at` column (rows are append-only). `on delete cascade` on `user_id` (deliberately different from `analytics_events`' `on delete set null` — justified in the migration's own comment: this table holds authenticated-only rows, so a deleted account's view history is deleted with it).

The `entity_consistency_check` is a DB-level backstop that mirrors `lib/activity/product-event-contracts.ts`'s own validation logic exactly (no `entity_id` without a matching, correctly-shaped `entity_type`), matching this repository's established "enforce the same invariant at every layer" convention (already used for Calendar Project/Client relationship rules earlier in this codebase's history).

## 7. Final RLS and grants

```sql
alter table public.authenticated_product_events enable row level security;

revoke all on table public.authenticated_product_events from public;
revoke all on table public.authenticated_product_events from anon;
revoke all on table public.authenticated_product_events from authenticated;

grant select, insert on table public.authenticated_product_events
  to service_role;
```

No `create policy` statements. No `update`/`delete` grant to any role. An authenticated application user cannot read even their own rows through PostgREST — every future read must go through an owner-only, `service_role`-executed RPC.

## 8. Final RPC signatures

Both in migration `202608030002`, both `language sql`, `stable`, `security invoker`, `set search_path = public` — matching `get_owner_user_activity_report()`/`get_owner_product_activation_analytics()`'s existing exact conventions.

### `public.get_owner_authenticated_activity_summary(p_user_ids uuid[])`

Returns a `jsonb` array of `{ user_id, last_seen_at, last_viewed_route, last_event_name, total_authenticated_views, distinct_active_days, is_returning }` for the given (server-capped at 2000) set of user ids.

**Argument choice, and why:** `p_user_ids uuid[]` was chosen over a no-argument bounded report. The existing Users & Activity page already computes one bounded, deduplicated, unioned set of user ids by merging `supabaseAdmin.auth.admin.listUsers()` with `get_owner_user_activity_report()` *before* any per-user enrichment happens. Passing that exact same id set into this RPC keeps every data source scoped to the identical bounded set deterministically. A no-argument "top N" report would instead apply its own independent ordering (e.g., "most authenticated views"), which could surface a *different* subset of users than the other two sources' own "top N by signup/profile date" ordering — silently breaking the merge's completeness for whichever user fell outside whichever independently-chosen window. Scoping by the caller's already-known id list also avoids aggregating rows for users who would not even appear in the final rendered table.

`distinct_active_days` is bucketed by `(created_at at time zone 'Asia/Jerusalem')::date`, matching the existing owner-analytics timezone convention (`lib/analytics/owner-analytics-window.ts`'s `OWNER_ANALYTICS_TIME_ZONE = "Asia/Jerusalem"`, and the "Times shown in Israel time" convention already on `/admin/analytics/users`). `is_returning := distinct_active_days > 1`, exactly as specified. The latest-event pick uses `distinct on (user_id) order by user_id, created_at desc, id desc` for full determinism on exact-timestamp ties.

### `public.get_owner_user_activity_timeline(p_user_id uuid, p_limit int default 200)`

Returns a `jsonb` array of `{ created_at, event_name, route, entity_type, entity_id }` for one user, newest first (`order by created_at desc, id desc` — deterministic even on exact-timestamp ties), with `p_limit` clamped server-side to a hard ceiling of 500 (`least(greatest(p_limit, 0), 500)`) regardless of the requested value.

Both functions revoke execution from `public`/`anon`/`authenticated` and grant only to `service_role`. Neither reads `auth.users` directly (matching `get_owner_user_activity_report()`'s own established pattern of merging Auth-schema fields in application code instead). Neither is called from any application code in this phase.

## 10. Validation behavior

The single entry point, `validateProductEventInput(input: unknown): ProductEventValidationResult`, never throws and never returns a partially-valid result.

1. **Shape**: parsed via a `zod` `.strict()` object schema (`RawProductEventInputSchema`) accepting only `eventName`, `route`, optional `entityType`, optional `entityId`. Any other key — including, but not limited to, `userId`, `createdAt`, `idempotencyKey`, or `metadata` — fails the whole parse (`reason: "invalid_shape"`), rather than being silently dropped. `zod`'s `safeParse` narrows `unknown` to a fully-typed result with **no unsafe cast anywhere in the module**.
2. **Route**: must start with `/` and not `//` (rejects `http(s)://` and protocol-relative URLs); query string and hash fragment are stripped (their content was never demonstrated to be needed); the *stripped* result is capped at 300 characters (`reason: "invalid_route"` if it fails any of these). A generous 10,000-character sanity cap is applied to the *raw* input before stripping, solely to reject pathological (multi-KB+) payloads — see §14 for why this number is not 2000, the value first attempted.
3. **Entity consistency**: an event requiring no entity rejects any supplied `entityType`/`entityId` outright (`reason: "unexpected_entity"`) rather than silently stripping it. An entity-requiring event rejects a mismatched `entityType` (`reason: "entity_type_mismatch"`), a missing `entityId` (`reason: "missing_entity_id"`), or a malformed one (`reason: "invalid_entity_id"`).
4. **Entity ID format**: `project`/`calendar_event` use the same RFC-4122-shaped UUID regex already used elsewhere in this codebase (`lib/analytics/signup-attribution.server.ts`'s `UUID_PATTERN`); `calendar_day` reuses `lib/tasks/date-only.ts`'s existing `parseDateOnly()` — the established, already-tested strict `YYYY-MM-DD` validator that rejects impossible calendar dates (e.g. February 30) — rather than a new, duplicate date validator.

`user_id` does not exist anywhere in the input contract's type or schema — it is structurally impossible for a caller to supply one through this module; it must be resolved server-side by whatever future route calls this validator.

## 14. Deviations from the mapping, and why

One implementation-time correction, caught by the module's own test suite (not a deviation from the *architecture* in the mapping document, only from an unstated implementation constant): the mapping's route-validation description said to strip query strings/hashes and cap the final route at 300 characters, but did not specify a defensive cap on the *raw*, pre-stripped input. The first implementation used `MAX_RAW_ROUTE_LENGTH = 2000` as a defensive guard against pathological input before doing any string work. A test explicitly required by this phase's own instructions — "does not reject an oversized route merely because of an incidentally huge query string" — failed against that value, because a legitimate short pathname (`/dashboard`) followed by a 5,000-character query string exceeded the raw cap *before* the query string was ever stripped, contradicting the requirement. The constant was raised to `10_000`, which comfortably accommodates any realistic query string while still rejecting truly pathological (multi-KB+) payloads outright. No other deviation from the mapping occurred.
